# 공방 메뉴(HUD) 입력과 갱신 (2026-11-20)

독립 QA에서 확인된 HUD 결함 5건(QA-01, QA-02, QA-04, QA-05, QA-06)의 원인, 바꾼 설계, 그리고 다시 생기지 않게 막는 테스트를 정리한다.
대상은 `scripts/workshop_hud.gd` 하나다. 저장 형식, 저장 키, 경제 계산, 월드 데이터는 바꾸지 않았다.

## 원인

| 결함 | 원인 |
|---|---|
| QA-01 수량 1 → 5 후 즉시 납품하면 1개 | 자유 납품 버튼의 콜백이 **그린 시점의** 수량(1)을 붙잡고 있었다. 입력값은 Enter나 포커스 이동 때만 반영됐다. |
| QA-02 상품을 바꾸면 수량이 1로 | 상품 선택 콜백도 그린 시점의 수량을 붙잡았다. 목록이 열려 있는 동안은 다시 그리기가 멈춰 있어 옛 콜백이 그대로 쓰였다. |
| QA-04 카드 본문 스와이프가 안 됨 | 카드(PanelContainer)와 버튼이 입력을 막아 스크롤 컨테이너까지 오지 않았다. 선택기는 누르는 순간 목록을 열었다. |
| QA-05 누르는 동안 갱신되면 동작 유실 | `_refresh()`가 게임이 바뀔 때마다 목록을 통째로 지우고 다시 만들었다. 누르고 있던 버튼이 사라져, 손을 떼도 아무 일도 없었다. |
| QA-06 갱신마다 전체 재생성 | 위와 같다. 틱마다 모든 행이 트리에 다시 들어갔다(테마 적용과 글자 모양 계산). 트리 밖에서 만드는 비용도 컸는데, 대부분은 입력칸의 한글 안내문 모양 계산이었다. |

## 설계

- **같은 탭의 다시 그리기는 행을 유지한다** (`_reconcile_rows`).
  - 새 목록은 트리 밖에서 그린 뒤 보이는 목록과 비교한다. 행은 첫 컨트롤의 id(없으면 첫 글자)로 순서대로 맞춘다.
  - 모양이 같은 행은 기존 컨트롤을 그대로 두고 값만 고친다(`_patch`: 글자, 사용 가능 여부, 선택, 토글).
  - 모양이 바뀐 행만 교체하고, 새 행은 끼워 넣고, 없어진 행은 뺀다.
  - 그래서 누르고 있는 버튼, 열린 목록, 포커스, 입력 중인 글자가 갱신을 견딘다. 탭을 바꾸면 예전처럼 새로 그린다.
- **누름과 팝업을 보호한다.**
  - 누르고 있는 동안이나 목록이 열려 있는 동안에는 값만 고치고, 행의 추가·삭제·교체는 손을 뗄 때(또는 목록이 닫힐 때) 바로 한다.
  - 입력 중인 칸이 있는 행은 교체하거나 빼지 않는다.
  - 표시는 계속 새 값으로 갱신되므로 낡지 않는다.
- **콜백은 지금 상태를 읽는다.**
  - 자유 납품의 상품·수량·납품은 그 순간의 선택기와 입력칸을 읽는다. 제작 목표는 지금의 목표값과 비교한다.
  - 다시 그려도 기존 컨트롤과 그 연결이 유지되므로, 콜백은 그린 시점의 값을 붙잡으면 안 된다.
- **자유 납품.**
  - 입력하는 즉시 선택이 갱신되어 미리보기(배송비·점수)가 실제 처리와 같다.
  - 납품은 사용자가 마지막으로 친 값으로 판단한다. 숫자가 아니거나 1~999999를 벗어나면 납품하지 않고, 보정된 숫자를 보여 준 뒤 다시 누를 때 보낸다.
  - 납품은 누른 다음 프레임에 실행한다. 웹 빌드는 키 입력을 클릭보다 한 프레임 늦게 넘기므로, 누르기 직전에 친 숫자까지 반영하기 위해서다.
  - 한 번 누르면 한 번 보낸다. 앞선 누름이 아직 보내지는 중(같은 프레임)에 들어온 누름만 버린다. 예전의 "400ms 안의 두 번째 누름 무시"는 빠른 정당한 연속 납품까지 막아 없앴다. 보내는 순간 재고·선택을 다시 읽으므로, 누른 뒤 재고가 사라지면 아무것도 보내지 않는다.
- **저장 탭 초안.**
  - 입력칸의 글은 탭을 다시 그려도 남는다(백업·복원용).
  - 가져오기(입력칸이든 파일이든)가 성공하면, 입력칸에 남은 글은 지우지 않고 "방금 가져오기 전에 있던 내용, 지금 게임의 저장이 아님" 표시를 붙인다.
  - 표시가 붙은 글로 '가져오기'를 누르면 한 번은 안내만 하고, 한 번 더 누를 때 가져온다. 글을 고치거나 내보내기로 채우면 표시가 사라진다.
  - 가져오기가 실패하면 입력칸과 게임은 그대로다. 표시는 성공(웹은 저장 완료) 신호(`workshop.imported`)에서만 붙는다.
- **스와이프.**
  - 목록 위에서 누른 채 세로로 8px 넘게 움직이면 스와이프로 보고 목록을 스크롤한다.
  - 그때 처음 누른 컨트롤에는 "포인터가 밖으로 나간 뒤 떼어짐"을 보내 동작하지 않게 한다.
  - 선택기는 손을 뗄 때 목록을 연다(버튼과 같은 방식).
  - 스크롤바와 입력칸에서 시작한 끌기는 예전 동작을 그대로 둔다. 마우스와 터치(마우스로 에뮬레이션됨) 모두 같은 경로를 쓴다.
- **위치 유지.**
  - 다시 그린 뒤에도 포인터 아래(없으면 포커스, 그다음 화면 맨 위) 컨트롤을 같은 화면 높이에 둔다(9227fe1).
  - 이번에 고친 것: 스크롤한 직후 같은 프레임에 다시 그리면 스크롤이 되돌아가던 문제. 기준점을 재기 전에 목록 위치를 먼저 반영한다.
- **행 id 구분.** 같은 화면에서 두 행이 같은 id를 쓰면 두 번째 행을 `method:id`로 구분한다(마을의 잔해 치우기 / 감정이 둘 다 `appraiser`였다).
- **브라우저 QA 보조.** `window.__trial_hud(command, argument)`는 컨트롤 위치와 목록 상태를 알려 준다(`open`만 탭을 연다).

## 저장 E2E delayed-confirmed 간헐 실패 (2026-11-20)

- 증상: `tests/web-save/run.cjs`의 delayed-confirmed가 부하가 걸리면 가끔 실패했다(24회 중 3회).
- 원인: 게임이 아니라 테스트였다. 첫 번째 쓰기를 풀어 준 뒤 저장소를 읽었는데, 느린 페이지에서는 그 사이에 두 번째 쓰기까지 끝나 "첫 커밋에는 첫 누름만"을 확인할 수 없었다.
- 고친 것: 커밋 완료 순간에 내용과 상태를 기록해 그것으로 판단한다. 두 번째 누름이 대기열에 들어간 뒤(두 rAF) 첫 쓰기를 푼다. 저장 로직과 형식은 바꾸지 않았다.
- 결과: 같은 부하에서 54회 중 54회 통과.

## 알려진 위험

- 모바일 터치 대상 높이는 28~32 CSS px로, 44px 권장보다 작다(86개 모두). 실제 기기 조작감은 확인하지 못했다.
- 실제 Android·iOS 기기는 확인하지 못했다(Chromium 모바일 에뮬레이션만).
- 버튼을 누른 채 다른 창으로 넘어가면(손을 뗀 신호가 오지 않음) 메뉴가 다음 클릭 때까지 "누르는 중"으로 남아 행 추가·삭제를 미룬다(값은 갱신됨). 돌아와서 하는 첫 클릭은 정상 동작하고, 누르던 버튼도 동작하지 않는다(브라우저에서 확인).
  - 포커스 해제 알림에서 누름을 놓는 수정을 시도했으나 되돌렸다. 웹판 Godot은 입력칸에 포커스가 있는 동안 IME 요소로 100ms마다 포커스를 옮기고, 그때마다 캔버스가 같은 알림(`NOTIFICATION_WM_WINDOW_FOCUS_OUT`)을 받는다. 그 알림이 클릭 도중에 오면 정상 클릭(수량 입력 뒤 자유 납품, 내보내기 뒤 가져오기)이 취소될 수 있었다. 이 수정을 넣은 뒤 CI의 HUD 브라우저 QA에서 "내보내기 뒤 가져오기" 확인이 한 번 실패했다.
